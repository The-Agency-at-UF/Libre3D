# Code Style & Conventions Guide

This guide documents the naming conventions, architectural patterns, and testing posture actually in use across the Libre3D codebase today. It reflects observed practice (there is no ESLint/Prettier config in the repo), so treat it as the de facto standard to match — not an aspirational one. See [CLAUDE.md](../CLAUDE.md) for architecture context and [project_index.md](project_index.md) for a file-by-file map.

## 1. Language & tooling baseline

- **TypeScript everywhere**, `strict: true`. Prefer explicit types on function signatures and props; let inference handle locals.
- **No linter or formatter is configured** (no `.eslintrc*`, no `prettier` config). There's no automated style enforcement — match the surrounding file's formatting by hand (2-space indent, double quotes, semicolons, trailing commas in multiline literals).
- The correctness bar is a clean `pnpm build` (`tsc -b && vite build`). There is no test suite (root `test` script is a stub) — see §6.
- Compiled artifacts (`*.tsbuildinfo`, `vite.config.js`/`.d.ts`, `awsPublishHandler.js`/`.d.ts`) are generated by the `tsc -b` composite build for `tsconfig.node.json`. Never hand-edit these; edit the `.ts` source and let the build regenerate them.

## 2. File & directory naming

- **React components**: `PascalCase.tsx`, one component per file, filename matches the exported component name (`HierarchyPanel.tsx` exports `HierarchyPanel`). Small presentational sub-components used only by one file (e.g. `HierarchyItem` inside `HierarchyPanel.tsx`) can live unexported in the same file rather than getting their own module.
- **Hooks**: `camelCase.ts` starting with `use`, matching the exported hook (`useViewportControls.ts` exports `useViewportControls`).
- **Manager classes** (imperative Three.js wrappers): `PascalCase.ts` matching the exported class (`SceneManager.ts` exports `SceneManager`).
- **Utility modules**: `camelCase.ts`, named after what they do, not what they contain (`exportScene.ts`, `publishScene.ts`), exporting a small set of named functions rather than a single default.
- **Factory modules** are named `createX.ts` for the thing they produce (`createAssetStore.ts`, `createGltfLoader.ts`, `createId.ts`) and export a `createX` function. Use this when two or more call sites need the same behaviour with different configuration, rather than a module of loose helpers each call site wires up itself.
- **Directory structure groups by architectural role, not by feature**: `components/`, `components/inspector/` (right-sidebar panels), `components/ui/` (generic, app-agnostic primitives), `hooks/` (app-level hooks), `viewport/` (Three.js manager classes), `viewport/hooks/` (viewport-specific hooks), `store/`, `utils/`, `styles/`. When adding a new file, place it by what kind of thing it is, matching this existing split.

## 3. Naming conventions (code)

- **Components & classes**: `PascalCase` (`ViewportCanvas`, `ObjectManager`, `CameraManager`).
- **Functions, variables, hooks, props**: `camelCase` (`updateSceneSettings`, `activeProfileId`, `handleExportAsset`).
- **Booleans** read as predicates: `isPreviewMode`, `isExporting`, `isCopied`, `hasSelection`, `showGrid`, `showAxisGuides`. Prefer `is`/`has`/`show` prefixes over bare adjectives.
- **Event handlers**: `handleX` for local handlers owned by a component (`handleExportAsset`, `handleColorChange`), `onX` for props/callbacks passed in (`onChange`, `onDuplicate`, `onNewFile`). A component's internal handler that wraps a prop callback is named `handleX` even if it just forwards to `onX`.
- **Store actions**: verb-first, matching the mutation they perform — `addEntity`, `removeEntity`, `updateEntityTransform`, `toggleVisibility`, `toggleLock`, `renameEntity`, `setActiveProfile`, `setPreviewMode`. Bulk/multi variants are named `updateMultiple*` (`updateMultipleEntityTransforms`) rather than overloading the singular action.
- **Types & interfaces**: `PascalCase`, no `I`-prefix (`Entity`, `EntityType`, `CameraProfile`, `SceneSettingsConfig`). Config-shaped interfaces end in `Config` (`PostProcessingConfig`, `FrameSettingsConfig`); prop-shaped interfaces end in `Props` (`ExportModalProps`, `TransformPanelProps`).
- **Constants**: `SCREAMING_SNAKE_CASE` only for true module-level constants that behave like enums or magic numbers (`ZERO_VECTOR`, `UNIT_VECTOR`, `DEFAULT_CAMERA_PROFILE_ID`, `HIDDEN_LAYER`). Config-defaults objects use `camelCase` with an `initial`/`DEFAULT` qualifier instead (`initialSceneDefaults`, `DEFAULT_CAMERA_PROFILE`).
- **Custom DOM events** dispatched via `window.dispatchEvent`/`addEventListener` use a `libre3d-` prefixed, kebab-case name (`libre3d-center-on-selected`, `libre3d-orientate-to-selected`) so they're clearly app-specific and won't collide with native events.
- **Global window escape hatches** are prefixed `__libre3d` (`window.__libre3dScene`) to signal "internal, not a public API" and avoid polluting `window`.

## 4. CSS conventions

- **Class names**: kebab-case, BEM-ish modifier suffixes with `--` (`editor-tree-item--selected`, `prop--stacked`), and conditionally-applied state classes built via template strings (`` `editor-tree-item${isSelected ? " editor-tree-item--selected" : ""}` ``).
- **CSS custom properties** (design tokens) live in `styles/tokens.css` under `:root`, kebab-case, semantically named by role rather than value (`--bg-panel`, `--text-secondary`, `--border-strong`, `--accent-dim`), not by raw color (`--blue`). Light theme overrides the same variable names under `:root.light-theme` — when adding a token, define it in both blocks.
- **Stylesheet split by concern**: `reset.css` (browser normalization) → `tokens.css` (variables) → `layout.css` (shell/grid structure) → `components.css` (everything else), imported in that order from `index.css`. New component styling goes in `components.css` unless it's structural shell layout.
- Inline `style={{ ... }}` objects are used liberally for one-off/dynamic styling (hover states, conditional colors) inside components, while anything reusable or static goes in a class in `components.css`. Follow the existing file's approach rather than mixing both heavily in one component.

## 5. Architectural patterns

- **Single source of truth**: all durable editor state lives in one Zustand store (`store/useEditorStore.ts`). Don't create parallel state stores; add fields to `EditorState` instead. Transient, non-persisted UI state (modal open, active tab, drag flags) belongs in local component state or the dedicated `useRightSidebarState` hook — never in the Zustand store.
- **Store mutations only through actions**: components read via `useEditorStore((state) => state.x)` selectors and mutate only by calling store actions (`addEntity`, `updateSceneSettings`, etc.), never by calling `useEditorStore.setState` directly from a component (the one exception, `App.tsx`'s `handleNewFile`, replaces the whole scene wholesale and is deliberately special-cased).
- **Deep-merge for nested config**: `sceneSettings`, `postProcessing`, and `frame` are nested objects updated exclusively through their `update*` actions (which deep-merge), never by spreading and replacing the whole object from a component. This is what lets new fields added to the defaults survive old persisted state.
- **Versioned persistence migrations**: any change to what's stored in `partialize` requires bumping `version` in the `persist` config and adding a matching `if (version < N)` block in `migrate`. Never assume a clean slate for existing users.
- **Imperative Three.js, not a scene-graph library**: there's no react-three-fiber. Scene/camera/object lifecycle is managed by plain classes (`SceneManager`, `CameraManager`, `ObjectManager`) instantiated once via `useMemo`, driven by `useEffect`s that diff store state against live Three.js objects. New Three.js side effects belong in one of these managers or a new manager class — not scattered `useEffect`s directly inside `ViewportCanvas.tsx` doing raw `THREE.*` calls, unless they're one-off UI concerns (resize, autoscale) that don't belong to any manager's responsibility.
- **Shared refs over cached values for the active camera**: renderer/controls/raycaster hooks all take a `cameraRef: RefObject<THREE.Camera>` and read `cameraRef.current` at use-time, rather than receiving the camera object as a prop. This is required for perspective↔orthographic switching to work without re-subscribing every hook. Follow this pattern for any new viewport hook that needs the active camera.
- **`window.__libre3dScene` as the escape hatch for the live scene**: export/publish code that needs the Three.js scene outside the component tree reads this global rather than having the scene prop-drilled or passed through context. Reuse this pattern for scene access from non-component code; don't introduce a second mechanism.
- **New entity types touch a fixed set of places**: `EntityType`/`Entity` (store), `ENTITY_DEFAULTS`, `createEntity` (store), and `ObjectManager`'s `createGeometry`/`createSceneObject`/`syncEntityToSceneObject`. When adding a type, update all of these together — missing one produces a type that exists in the store but renders or defaults incorrectly.
- **Configure one implementation rather than copying it.** `modelAssetStore` and `textureAssetStore` are ten-line bindings of the `createAssetStore` factory, differing only in their storage names and a `decode` hook. They began as byte-for-byte copies and drifted into needing the same fix twice — the OPFS migration and the IndexedDB fallback each had to be written, reviewed, and verified in two files. When a second call site needs behaviour you already have, parameterise the difference rather than duplicating the whole module; the rule of three applies, but two modules that have already changed in lockstep are past it.
- **Binary payloads never enter the store.** Anything too large for `localStorage` — imported `.glb` buffers, texture bitmaps — is written through a `createAssetStore` binding, and the entity persists only its id (`assetId`, `textureAssetId`). Adding a new kind of large asset means adding a binding, not a new storage mechanism. See [architecture.md §7](architecture.md).
- **Vector fields are always cloned**, never referenced. `cloneVector`/`cloneEntity`/`cloneCameraProfile` exist specifically so callers can't mutate a `position`/`rotation`/`scale` tuple in place and corrupt store state. Any new code reading or writing these fields should clone on the way in and out.
- **Props over context**: cross-component data flow is via explicit props (see `App.tsx` → `ExportModal`/`RightSidebar`) or direct Zustand selectors, not React Context. Add a new Zustand slice/selector rather than introducing a Context provider.
- **No default exports**: components, hooks, managers, and utils are all named exports. Match this — avoid `export default`.

## 6. Testing requirements

- **There is currently no test suite.** The root `test` script is a stub (`echo "Error: no test specified" && exit 1`), and no test runner (Vitest, Jest, etc.) is configured in either `package.json`.
- **The correctness bar is a clean build plus manual verification**, per the README's review workflow:
  1. `pnpm build` (or `pnpm --filter editor build`) must pass with no `tsc` errors.
  2. Run `pnpm dev`, exercise the feature manually in the browser, and check the devtools console for WebGL/GLTF warnings or errors.
  3. Confirm existing functionality (selection, transform gizmo, undo/redo, publish/export) still works — there's no regression suite to catch this automatically.
- If you introduce a test runner or write the first tests, document the chosen framework and `pnpm test` invocation here and in `CLAUDE.md` — don't assume a future reader knows how to run them.

## 7. Commit & PR conventions

- **Branch naming**: `[initials]/[feature-name]` (e.g. `em/add-sandbox-viewport`).
- **Commit messages**: Conventional Commits style, `type: short description` (`feat: ...`, `fix: ...`, `refactor: ...`), imperative mood, one logical change per commit.
- **PRs**: opened against `main`, must have `pnpm build` passing and a manual dev-server smoke test completed before requesting review (see §6).
