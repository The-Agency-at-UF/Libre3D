# GLB Import Pipeline — Optimization & Feature Plan

Working plan for reworking the `.glb` import pipeline (`utils/importModel.ts`, `utils/modelAssetStore.ts`, `utils/gltfHierarchy.ts`, `store/useEditorStore.ts`'s `addImportedModelHierarchy`, `viewport/ObjectManager.ts`'s `hydrateImportedModel`). Covers the performance issues already identified plus three new requirements: ungrouping imported hierarchies, filtering empty/pass-through nodes on import, and giving every imported node a real, editable material.

## Grounding: how Spline handles the same problems

Since Libre3D is explicitly built as an open alternative to Spline, it's worth matching their model where it's proven rather than inventing a new one:

- **Materials are layer stacks.** Every object gets a Color layer and a Lighting layer by default — this is exactly Libre3D's existing `ColorLayer`/`LightingLayer` split. Textures are *not* a special material mode; they're an **Image Layer** added to the same stack, with its own settings (UV/Planar/Spherical/Cylindrical/Triplanar projection, wrap mode, scale/offset/rotation). Bump and roughness maps are just image layers pointed at those channels. This validates extending `MaterialLayer` with a new `"image"` variant rather than building a parallel texture system.
- **Spline's import hygiene advice is manual — but it's advice about a *lossy* operation.** Its CAD-import guide tells users to decimate polygons and merge parts before export, which is a real visual tradeoff, so it makes sense that Spline leaves it to the user rather than doing it silently. It also ships a Performance Panel (stats, compression toggles, "Remove Unused Assets") as the deliberate, user-invoked side of that same coin. **Our empty/pass-through-node pruning is not the lossy kind** — it changes zero geometry, zero materials, zero pixels; it only removes bookkeeping nodes that render identically with or without them. That distinction is why Phase 3 below defaults to doing this automatically at import time (see revision note there), while still keeping a manual re-run action and adding our own Phase 5 performance panel.

## Phase 0 — Fix the double parse (foundation, no behavior change) ✅ done (`954a8e5`, `em/glb-single-parse`)

The one everyone should agree on immediately. `prepareModelImport` parses the buffer once just to extract names/transforms; `ObjectManager.hydrateImportedModel` parses the *same buffer* again for real geometry/materials moments later.

- Have `prepareModelImport` do the single `GLTFLoader.parse`, build `ImportNodeSpec[]` from the result it already has in hand, and keep the parsed `gltf` around (short-lived, in-memory, keyed by `assetId`) so the very first hydrate doesn't re-fetch-and-reparse.
- `ObjectManager.hydrateImportedModel` still needs to be able to parse from `assetId` on its own for the *reload* case (persisted transforms, no live parsed object available) — that path is legitimate and stays.
- Test: import a model, confirm only one `GLTFLoader.parse` call fires (add a temporary console count or check via devtools performance trace), confirm visual output identical to today.

## Phase 1 — Decoders + storage backend ✅ done (`60ef5c4`, `6e9e8bb`, `160a655`, `em/glb-decoders-and-opfs`)

- **Register `DRACOLoader`, `KTX2Loader`, `MeshoptDecoder`** on both `GLTFLoader` instances (`importModel.ts` and `ObjectManager.ts`) via `setDRACOLoader`/`setKTX2Loader`/`setMeshoptDecoder`. Without this, any compressed `.glb` (increasingly common — Meshopt/Draco can cut geometry size 90%+) fails to import at all today.
- **Move the raw buffer from IndexedDB to OPFS.** IndexedDB pays the structured-clone cost on every write (~850ms for 100MB in published benchmarks) vs. OPFS's `createSyncAccessHandle` (~90ms for the same). OPFS has shipped in all major browsers since 2023, so this is a safe swap, not a progressive-enhancement fork. `modelAssetStore.ts`'s three functions (`saveModelAsset`/`loadModelAsset`/`deleteModelAsset`) keep the same signatures — only the implementation changes.
- **Actually call `deleteModelAsset`.** It exists today and is never invoked. Wire it into `removeEntity` (or wherever entity deletion is finalized) so deleting an imported model's root also frees its stored buffer — otherwise every deleted import leaks storage forever, and that leak gets worse once buffers are the size Draco/Meshopt-compressed files tend to be.

**As actually implemented:** a shared `createGltfLoader.ts` factory (`createConfiguredGltfLoader()`) wires all three decoders identically at both call sites, so there's one place to maintain instead of two. `KTX2Loader.detectSupport()` needs a live `WebGLRenderer` that `importModel.ts` has no access to (it's a standalone utility, no viewport) — fixed by having `useViewportRenderer.ts` expose `window.__libre3dRenderer`, mirroring the existing `window.__libre3dScene` escape hatch (see `conventions.md` §5); if it's unavailable, KTX2 registration is skipped with a `console.warn` rather than throwing. `createSyncAccessHandle` turned out to be worker-only by spec with no main-thread path and no indication that's changing — since there's no worker in the codebase yet (that's Phase 4), the OPFS move uses the async main-thread API (`getFileHandle`/`createWritable`/`getFile`) instead, which avoids IndexedDB's structured-clone tax but doesn't hit the dramatic sync-API benchmark numbers.

**Real-world note on KTX2 specifically:** checked adoption while testing this — it's genuinely uncommon in single-file `.glb`s in the wild. Blender's official exporter doesn't produce it without a third-party addon, and even Khronos's own sample-asset library only ships its KTX2 example as a multi-file `.gltf`, not a plain `.glb`. Draco and Meshopt are verified working end-to-end with real fixtures (both declare their extension as *required*, so both went from a hard failure to rendering correctly); KTX2's code path is in place and doesn't regress anything else, but is unverified against a real KTX2-textured import. Low cost to keep, low priority to chase further verification on.

**Known tradeoff, fix moved up to Phase 2.5 below (done immediately, ahead of Phase 3):** Part C's immediate `deleteModelAsset` call means undo (Ctrl+Z, via zundo) after deleting an imported model restores the entity but not its buffer — it re-hydrates as the red error box instead of the working model. See Phase 2.5.

## Phase 2 — Every imported node gets a real, editable material ✅ done (`c4ea3d3`, `9f9583c`, `em/glb-editable-materials`)

This is the largest phase. Today `MaterialsPanel.tsx` explicitly filters out `type === "importedModel"` entities — imported meshes render with their raw parsed `THREE.Material` and are completely un-editable. Goal: every imported mesh entity gets a populated `materialLayers` array derived from its actual glTF material, following Spline's layer model.

1. **Extend `MaterialLayer`** with a new `ImageLayer` variant (`type: "image"`): `{ id, type: "image", enabled, opacity, textureAssetId, slot: "color" | "normal" | "roughness" | "metalness" | "emissive" | "ao", ... }`. MVP scope: UV-projection only (glTF already bakes UVs — no need for Spline's Planar/Spherical/Cylindrical projection modes yet), plus whatever `wrapS`/`wrapT` the source material already used. Projection modes are a later nice-to-have, not required for parity with what a `.glb` can already express.
2. **Don't inline texture pixels into `materialLayers`.** That array is persisted straight to `localStorage` via the store's `persist` middleware — a single embedded texture could be megabytes and blow the quota immediately. Instead, at import time, extract each unique texture image from the parsed glTF, save it into an asset store keyed by a new `textureAssetId` (same OPFS-backed store as Phase 1, or a sibling store), and have `ImageLayer` reference that id. This mirrors the existing `assetId` pattern for the whole model — don't invent a second storage mechanism per the "don't introduce a second state mechanism" rule.
3. **Derive layers at hydrate time.** In `ObjectManager.hydrateImportedModel`, for each resolved mesh, read its parsed `THREE.Material` (`.color`, `.roughness`, `.metalness`, `.emissive`, `.emissiveIntensity`, `.map`, `.normalMap`, `.roughnessMap`, etc.) and build the equivalent `ColorLayer` + `LightingLayer` (+ `ImageLayer`s where maps exist), matching lighting model from the material's constructor the same way `materialClassForModel` already maps the reverse direction.
4. **Backfill existing imports.** Anyone who imported a model before this ships has `materialLayers: undefined` on those entities. This can't be handled in the `persist` `migrate` function (no parsed glTF data available at migration time) — it has to happen the first time `hydrateImportedModel` runs post-upgrade: if a resolved entity has no `materialLayers`, derive and write them back via a new store action (e.g. `setEntityMaterialLayers`) instead of leaving it permanently un-editable. Bump the persist `version` regardless, since `Entity`'s shape effectively gains a populated field for a whole class of existing entities.
5. **`ObjectManager.syncEntityToSceneObject`** currently has an explicit early-out for imported meshes ("carry no materialLayers ... skip the layered-material sync so their original glTF materials aren't overwritten"). Once they *do* carry layers, that comment and the branch need to go — but `createMaterialFromLayers` needs to grow texture-map support first (assign `material.map`/`.normalMap`/etc. from a resolved `THREE.Texture`, loaded once and cached against `textureAssetId`, not re-decoded every sync).
6. **`MaterialsPanel.tsx`**: drop the `type !== "importedModel"` filter; add an "Image" layer row (thumbnail + upload/replace + slot picker) alongside the existing Color/Lighting rows.

Flag: this phase touches persisted shape, a new layer type, `ObjectManager`, and `MaterialsPanel` together — per `conventions.md` §5 ("new entity/layer types touch a fixed set of places together"), do it as one deliberate pass, not incrementally, so nothing's left half-wired.

**Gap found post-implementation, fixed in Phase 2.5 below:** `textureAssetStore.ts`'s `deleteTextureAsset` was added and correctly deletes a blob given an id, but nothing ever calls it — it's never wired to entity deletion the way `deleteModelAsset` is (or, after Phase 2.5, isn't — see below). Every deleted imported mesh's derived textures leak in OPFS forever. Same class of bug as Phase 1's original `deleteModelAsset` gap, not a rare edge case.

## Phase 2.5 — Asset & texture storage cleanup (prioritized ahead of Phase 3)

Done immediately after Phase 2 rather than deferred to Phase 5, since it fixes two known-live problems at once: Phase 1's undo-breaking immediate `deleteModelAsset` call, and Phase 2's `deleteTextureAsset`-never-called leak. Both are storage-lifecycle bugs in code that already shipped, not new scope — fixing them now means Phase 3 (hierarchy) starts on a clean base instead of carrying two open leaks forward.

**Design: replace delete-time cleanup with an app-load reconciliation sweep.**

1. **`removeEntity` goes back to being a pure reducer.** Remove Phase 1 Part C's fire-and-forget `deleteModelAsset(entity.assetId)` loop entirely — deleting an entity no longer touches OPFS in the moment, for either model or texture assets. This is what fixes the undo regression: zundo's undo history is in-memory/session-scoped and never persisted, so as long as nothing is deleted from OPFS until the *next* app load, Ctrl+Z always restores a fully working entity for the rest of the session, no matter how long the user waits before pressing it.
2. **Add `listModelAssetIds()` to `modelAssetStore.ts` and `listTextureAssetIds()` to `textureAssetStore.ts`.** Both directories already exist (`libre3d-models`, `libre3d-textures`); add a function that opens the directory (`create: false`, treating a missing directory as an empty list via the existing `isNotFound` helper) and returns the entry names via `for await (const name of dir.keys())`.
3. **New `utils/assetReconciliation.ts` exporting `reconcileAssetStorage(entities: Entity[]): Promise<void>`.** Takes entities as a plain parameter (not read from the store) to avoid a circular import between the store and this util. Computes two referenced-id sets by walking `entities`: every `entity.assetId` where defined (model assets), and every `textureAssetId` on every `ImageLayer` inside every `entity.materialLayers` (texture assets). Lists actual OPFS contents via the two new `list*AssetIds()` functions, and for anything on disk but not in the referenced set, calls the existing `deleteModelAsset`/`deleteTextureAsset`. Log a one-line summary (count freed) — useful during rollout, cheap to keep.
4. **Wire it via `useEditorStore.ts`'s `persist` `onRehydrateStorage` option**, so it runs once per app load right after the persisted state is available: `onRehydrateStorage: () => (state) => { if (state) void reconcileAssetStorage(state.entities); }`. This is the "next reload" point where it's now safe to actually free anything — the persisted store at that moment already reflects whether any given deletion was undone before the user closed the tab.
5. **Keep `reconcileAssetStorage` exported and reusable** — Phase 5's "Remove Unused Assets" manual button becomes a thin wrapper calling this same function on demand (for anyone who wants to reclaim space without reloading), not a second implementation.

Worst case under this design: a deleted-and-not-undone import's buffer sits unused in OPFS until the next reload, not a permanent leak. That's a strictly better failure mode than either of the two problems it replaces (broken undo, or a leak with no cleanup path at all).

## Phase 3 — Hierarchy cleanup: ungroup + fully-automatic node pruning

**Revised per feedback: no manual "Clean Up Hierarchy" button.** Pruning must be complete and correct at parse time, with no user-facing fallback action to lean on if it misses something — the internal parse has to just be efficient/thorough enough that the user never needs to do extra work or press another button.

**Extend `ungroupEntity`.** Today it hard-guards `entity.type !== "group"` and no-ops for anything else — so imported hierarchies can't be ungrouped at all. `entityIndex.ts`'s `canReparentEntities` already allows reparenting *within* an imported model's subtree (it only blocks a node from leaving its `rootEntityId` chain) — confirmed directly: dragging a node to a new position *within* the same import's hierarchy panel subtree already works today via the ordinary `reparentEntities` action, only leaving the subtree is blocked. That means the underlying reparent-with-preserved-world-transform math (`getEntityWorldMatrix`/`solveLocalFromWorld`) is already exercised, generic, and entity-type-agnostic — `ungroupEntity`'s fix really is just loosening its type guard to also allow `entity.type === "importedModel" && entity.id !== entity.rootEntityId` and reusing its existing reparent-children-then-remove-node logic as-is. No new reparenting logic needed.

**The import root itself stays protected** — its `assetId` is the only pointer back to the stored buffer, and every other node in the import resolves against it via `rootEntityId`. Ungrouping the root would orphan the whole hierarchy on next reload. If you want a "fully detach this import from its source file, convert every node into independent standalone entities" feature later, that's a distinct, heavier operation (baking geometry/materials permanently, severing `nodePath`/`rootEntityId` entirely) — call it out separately if you want it; not included here.

**Auto-prune runs automatically on import, with zero manual fallback.** Pruning empty/pass-through nodes isn't lossy: a wrapper's transform gets baked into its surviving child and a truly empty leaf just disappears, with zero change to the rendered result — so there's no reason to make the user ask for it. This is also the direct answer to the original ask ("filter out empty nodes on the initial parse so we only import what is needed").

- Walks the parsed node tree (in the same single-parse pass from Phase 0 — no extra parse needed) and identifies two categories: **pass-through wrappers** (exactly one child, no mesh of its own) and **dead leaves** (no mesh, no children).
- **Deliberately conservative on multi-child empty nodes.** A no-mesh node with *more than one* child (e.g. an organizational "Wheels" group holding four wheel meshes) is left alone even though collapsing it would still be lossless rendering-wise. Single-child wrappers are almost always DCC-export cruft nobody named on purpose (e.g. Blender's axis-conversion empties); multi-child empty nodes are more likely a meaningful, user-authored organizational label worth keeping visible in the hierarchy panel. Revisit this case-by-case if a real model surfaces a multi-child node that's clearly cruft too, rather than broadening the rule preemptively.
- **Must exempt bones.** A `Bone` referenced by any `SkinnedMesh.skeleton.bones` in the file has no mesh and often no distinguishing feature besides its name/position, but removing it breaks skinning. Tag `isBone`/`isProtected` on `ImportNodeSpec` at extraction time (the single-parse pass already has the full skeleton data in hand) so this pass consults one flag instead of re-deriving skeleton membership.
- Collapsing a wrapper bakes its local transform into its child's local transform (matrix compose, not just a `parentId` swap) so the child renders in the identical position once the wrapper is gone.
- **Pre-existing imports (persisted before this shipped) get pruned too, with no manual action required.** Same backfill pattern Phase 2 already established for `materialLayers`: the first time an already-persisted import is hydrated post-upgrade, run this identical prune pass against its currently-resolved node entities and collapse anything eligible, writing the result back via a store action — exactly how `backfillMaterialLayers` retroactively derives layers for old imports the first time they're re-hydrated. This closes the gap the removed manual button used to cover.
- `ungroupEntity`'s extension above stays a manual, one-node-at-a-time action — that's a deliberate user restructuring choice (e.g. flattening a branch they want gone permanently for editing reasons), not dead-weight removal, so it keeps its explicit trigger. It's unaffected by removing the prune button.

## Phase 4 (stretch, do last) — Worker-offloaded parsing

Only worth it once import files are large enough to visibly jank the UI thread. Real cost: `GLTFLoader` doesn't have official worker support — confirmed via open three.js GitHub issues (#15090, #18765) — getting it working requires mocking DOM APIs (`document.createElement`, etc.) inside the worker. Sequence this after everything else; it's the highest-effort, lowest-certainty item here.

## Phase 5 — Performance panel

Nothing structural blocks this — it's additional scope, not a hard problem, and most of the data it needs is already computed elsewhere in the codebase. For Libre3D, a first version would hold:

- **Live scene stats**: entity count, total triangle count, rough texture memory estimate — computed by walking `window.__libre3dScene`, the same traversal `exportScene.ts`'s `hasExportableMeshes` already does, just tallying instead of counting.
- **"Remove Unused Assets" button**, mirroring Spline's version: a manual, on-demand trigger for the same `reconcileAssetStorage` sweep Phase 2.5 already built and wired to run automatically on app load. This just gives users a way to reclaim space without reloading — no new sweep logic, a thin UI wrapper over the existing function.
- **Export-time compression toggles**: re-encode with Draco/Meshopt/KTX2 through `GLTFExporter`'s own extension options when downloading a `.glb` — the export-side mirror of the Phase 1 import decoders, so round-tripping a model doesn't silently balloon its file size back up.

Sequence this whenever it's wanted — it has no hard dependency on Phases 2–4; the "unused assets" button just calls Phase 2.5's already-built sweep.
